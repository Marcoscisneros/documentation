When an API request cannot be completed, the Pizzeria Co API returns a machine-readable error object that tells you exactly what went wrong. Understanding this format and the corresponding HTTP status codes lets you handle failures gracefully and build resilient integrations from the start.

## Error Response Format

All error responses use a consistent JSON structure. The top-level `error` object contains three fields:

<ResponseField name="error.code" type="string" required>
  A stable, snake_case identifier for the error type. Use this field in your application logic to branch on specific failure conditions — `message` is intended for humans and may change.
</ResponseField>

<ResponseField name="error.message" type="string" required>
  A human-readable description of the error, often including relevant context such as a resource ID or current state.
</ResponseField>

<ResponseField name="error.details" type="object">
  An optional object with structured metadata about the error. The keys vary by error type and give you the information needed to resolve the issue without parsing the `message` string.
</ResponseField>

```json title="Example error response"
{
  "error": {
    "code": "machine_not_idle",
    "message": "Machine mch_01hx3k9 is currently running and cannot be started.",
    "details": {
      "machine_id": "mch_01hx3k9",
      "current_status": "running"
    }
  }
}
```

<Tip>
  Always branch on `error.code` in your code, not on `error.message`. Messages are human-friendly and may be updated over time, while codes are stable across API versions.
</Tip>

## HTTP Status Codes

The HTTP status code of the response gives you the first signal about how to categorize and respond to an error.

### Success Codes

| Status | Meaning |
|--------|---------|
| `200 OK` | The request succeeded. The response body contains the requested data. |
| `201 Created` | A new resource was successfully created. The response body contains the created resource. |

### Client Error Codes

| Status | Meaning |
|--------|---------|
| `400 Bad Request` | The request body is invalid or is missing required fields. Check `error.message` for the specific field or constraint that failed. |
| `401 Unauthorized` | Your API key is missing or invalid. Verify that you are passing a valid Bearer token in the `Authorization` header. |
| `403 Forbidden` | Your API key is valid but does not have permission to perform this action. Check the key's assigned scopes in your dashboard. |
| `404 Not Found` | The requested resource does not exist, or your API key does not have access to it. |
| `409 Conflict` | The operation conflicts with the current state of a resource — for example, attempting to start a machine that is already running. |
| `422 Unprocessable Entity` | The request is syntactically valid but semantically incorrect — for example, referencing an ingredient quantity of zero in a recipe. |
| `429 Too Many Requests` | You have exceeded the rate limit. Check the `Retry-After` header for how many seconds to wait before retrying. See [Rate Limits](/api-reference/rate-limits) for details. |

### Server Error Codes

| Status | Meaning |
|--------|---------|
| `500 Internal Server Error` | An unexpected error occurred on our side. If this persists, contact [support@pizzeriaco.com](mailto:support@pizzeriaco.com) with the request details and timestamp. |

<Warning>
  A `404 Not Found` response does not necessarily mean the resource has never existed — it may also be returned when your API key lacks access to an existing resource, to avoid leaking information.
</Warning>

## Machine-Specific Error Codes

The following `error.code` values are specific to machine and production run operations. You should handle these explicitly in any integration that controls factory equipment.

| Code | Description |
|------|-------------|
| `machine_not_idle` | The target machine must be in an `idle` state before it can be started. Check `error.details.current_status` to see its current state. |
| `machine_in_maintenance` | The machine is currently under maintenance and cannot accept commands. Check your maintenance schedule or contact your operations team. |
| `recipe_in_use` | The recipe cannot be deleted because it is associated with one or more active production runs. Complete or cancel those runs first. |
| `insufficient_inventory` | There is not enough of one or more ingredients to fulfil this production run. Check `error.details` for the affected ingredient IDs and shortfalls. |
| `invalid_recipe_id` | The specified recipe ID does not exist or is not accessible with your API key. Verify the `rec_` prefixed ID before retrying. |

## Handling Errors in Practice

The example below shows a pattern for inspecting the error code and responding accordingly in JavaScript.

```javascript title="Error handling example (JavaScript)"
const response = await fetch("https://api.pizzeriaco.com/v1/machines/mch_01hx3k9/start", {
  method: "POST",
  headers: {
    "Authorization": "Bearer <your_api_key>",
    "Content-Type": "application/json",
  },
});

if (!response.ok) {
  const { error } = await response.json();

  switch (error.code) {
    case "machine_not_idle":
      console.error(`Cannot start machine — current status: ${error.details.current_status}`);
      break;
    case "machine_in_maintenance":
      console.error("Machine is under maintenance. Check your schedule.");
      break;
    case "insufficient_inventory":
      console.error("Not enough ingredients to start this run.", error.details);
      break;
    default:
      console.error(`Unexpected error [${error.code}]: ${error.message}`);
  }
}
```
